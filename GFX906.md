# gfx906 (AMD Instinct MI50/MI60) build notes

This fork carries the minimum changes needed to build a ROCm 10 distribution from
TheRock targeting `gfx906` only, which isn't an officially supported target upstream
(official support starts at gfx908).

## Source changes

None. This fork currently carries no source changes vs upstream `main`; it only adds
this document.

Earlier revisions force-disabled the `rccl-translate` gfx1250-unbundle step in
`comm-libs/CMakeLists.txt`, because it failed with
`No code objects for architecture 'gfx1250'` when RCCL was scoped to gfx906 only.
Upstream fixed this properly in ROCm/TheRock#8279 (the pretranslate step is now
skipped when gfx1250 isn't in RCCL's target list), so the local hack was dropped.

## Building in Docker (Unraid or any host without a toolchain)

`build-gfx906-docker.sh` runs the recipe below inside an Ubuntu 24.04
container. Everything (sources, venv, ccache, build tree) stays in the
checkout, so re-running it resumes an interrupted build.

```bash
git clone https://github.com/Wizard815/TheRock-gfx906.git
cd TheRock-gfx906
JOBS=4 ./build-gfx906-docker.sh
```

Needs ~250GB free in the checkout and roughly 4-8GB RAM per job. On Unraid,
clone onto a cache/pool disk path (e.g. `/mnt/cache/...`) rather than a
`/mnt/user/...` share that lives on the parity array — the build does
millions of small writes. `./build-gfx906-docker.sh shell` opens a shell in
the same build environment.

## Build recipe (Linux / WSL2 Ubuntu 24.04)

```bash
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
# meson 1.12.0's duplicate --version-script regression is fixed upstream
# (ROCm/TheRock#7287, #7489); pin meson==1.11.2 only if you hit it again.
python3 ./build_tools/fetch_sources.py

eval "$(./build_tools/setup_ccache.py)"
export CMAKE_BUILD_PARALLEL_LEVEL=4   # -j on the CLI does NOT propagate to nested
                                       # per-subproject `cmake --build` calls; this
                                       # env var does, and is what actually caps
                                       # parallelism enough to avoid OOM on a 20-core/
                                       # limited-RAM WSL VM.

cmake -B build -GNinja \
  -DTHEROCK_AMDGPU_FAMILIES=gfx906 \
  -DTHEROCK_TEST_AMDGPU_TARGETS=gfx906 \
  -DTHEROCK_ENABLE_ROCWMMA=OFF \
  -DTHEROCK_ENABLE_HIPBLASLTPROVIDER=OFF \
  -DTHEROCK_ENABLE_ROCJITSU=OFF \
  -DTHEROCK_ENABLE_EMULATION=OFF \
  -DCMAKE_C_COMPILER_LAUNCHER=ccache \
  -DCMAKE_CXX_COMPILER_LAUNCHER=ccache

ninja -C build -j4
ninja -C build artifacts
ninja -C build archives
```

Output: `build/dist/rocm/` — a self-contained ROCm 10 install tree for gfx906.

## Disabled components

These are turned off because they do nothing for gfx906 and only add build time
(same set used by [mixa3607/ML-gfx906](https://github.com/mixa3607/ML-gfx906/blob/master/rocm/BUILD-PACKAGES.md)):

- `ROCWMMA` — wraps matrix-core (MFMA/WMMA) instructions; gfx906 has none.
- `HIPBLASLTPROVIDER` — hipDNN provider on top of hipBLASLt, which has no gfx906 kernels
  (see below).
- `ROCJITSU` / `EMULATION` — rocJitsu emulation/translation tooling, aimed at newer archs.
  With these off, the `rccl-translate` step isn't configured at all.

## Stable vs. development sources

`main` tracks the next ROCm in development (`version.json` → 10.2.0 at the time of
writing). For a more predictable build, check out an upstream release branch instead,
e.g. `release/therock-10.1`, and apply this document's flags; the flags have no source
changes to carry.

## hipBLASLt and gfx906

hipBLASLt does not support gfx906: upstream excludes it from
`tensilelite_supported_architectures.cmake`, there is no `vega20` logic, and TheRock
builds the target-neutral hipBLASLt subproject only for `gfx1100`. The resulting
install has `lib/rocblas/library/gfx906` but no `lib/hipblaslt/library/gfx906`.

Practical effect:

- Ordinary FP16/BF16/FP32 GEMMs (llama.cpp, whisper.cpp, PyTorch `matmul`) go through
  rocBLAS and work.
- Anything that calls hipBLASLt directly fails at heuristic selection — e.g. PyTorch
  `torch._int_mm` (INT8), and `TORCH_BLAS_PREFER_HIPBLASLT=1`. Keep PyTorch on rocBLAS
  (`TORCH_BLAS_PREFER_HIPBLASLT=0`) and avoid INT8 weight-only quant paths that need
  `_int_mm`.

Details: [ML-gfx906 HIPBLASLT-GFX906.md](https://github.com/mixa3607/ML-gfx906/blob/master/rocm/HIPBLASLT-GFX906.md).

## Notes

- `THEROCK_TEST_AMDGPU_TARGETS=gfx906` (not the default, which builds RCCL for ~24
  architectures) scopes RCCL to gfx906 only — this is what you want if you just need
  multi-GPU communication between MI50/MI60 cards and don't care about other archs.
- `./build_tools/fetch_sources.py` resets all submodules and reapplies patches — it is
  **destructive** to any uncommitted submodule changes. Commit first.
- Long builds should be detached with `setsid nohup ... & disown` (not plain `&`) if run
  inside a `wsl.exe` invocation from a Windows host, or they die when the parent process
  exits.
